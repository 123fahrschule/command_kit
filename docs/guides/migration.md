# Migrating an Existing Service

This guide shows how to move an existing service (using `Shared.EventStore.Metadata`,
`Shared.URN`, and keyword-list application services) to CommandKit — one
application service at a time, not big bang. Old and new code coexist safely
during the whole migration: `%CommandKit.Metadata{}` persists as the same
flat metadata map (`causation_id`, `correlation_id`, `enacted_by`,
`occurred_at`, `received_at`) that `Shared.EventStore.Metadata.for_command/2`
produces today, so event projections, publishers, and consumers keep working
regardless of which side wrote the event. Event stores that normalize
metadata with `Enum.into(metadata, %{})` — like ours — accept the struct
directly.

## Concept mapping

| Today                                              | With CommandKit                                           |
| -------------------------------------------------- | --------------------------------------------------------- |
| `execute(keyword_list)` application service        | Command module (`params do`) + handler `execute(command)` |
| `event_metadata("add-employee-absence", metadata)` | `command.metadata`, passed to `append_event` directly     |
| Command name as string, checked at runtime         | `command_name/0`, derived from the module, overridable    |
| `Shared.URN.generate(command)`                     | Generated in `new/1` from `source:` + name + `command_id` |
| `extract_event_metadata(event)` in consumers       | `CommandKit.Command.caused_by(command, event)`            |
| `metadata_caused_by_event(event_name, metadata)`   | `CommandKit.Metadata.caused_by_event(metadata, event_name, id, MyApp.Command)` |

## Step 1: Base modules and configuration

Add the dependency and define the base modules. Nothing else changes yet —
existing code keeps running untouched.

```elixir
# mix.exs
{:command_kit, "~> 0.1.0"}
```

```elixir
defmodule MyApp.Command do
  # the same URN prefix Shared.URN produces today, e.g. "de.123fahrschule:absence"
  use CommandKit.Ecto.Command, source: "de.123fahrschule:my_app"
end

defmodule MyApp.CommandBus do
  use CommandKit.Bus, otp_app: :my_app
end
```

```elixir
# config/config.exs
config :my_app, MyApp.CommandBus,
  default_pipeline: :default,
  pipelines: [
    default: [
      CommandKit.Middleware.Telemetry,
      CommandKit.Middleware.Logging,
      CommandKit.Middleware.ErrorHandler
    ]
  ]
```

The `source:` must match the URN prefix your service writes today, so URNs
generated by CommandKit are indistinguishable from existing ones in the event
store.

## Step 2: Migrate one application service

Take one application service and convert it end to end: command module,
handler, and its call sites. Everything else stays on the old path.

Before — keyword-list service, metadata threaded by hand:

```elixir
defmodule Absence.AddEmployeeAbsence do
  use Absence, :application_service

  def execute(
        employee_id: employee_id,
        absence_reason_id: absence_reason_id,
        # ... many more entries ...
        metadata: metadata
      ) do
    # domain logic ...

    start_transaction()
    |> persist_employee_absence(employee_absence)
    |> persist_event(event, metadata)
    |> finish_transaction()
    |> return_result()
  end

  defp persist_event(multi, event, metadata) do
    Multi.run(multi, :employee_absence_added_event, fn _, _ ->
      append_event(event, event_metadata("add-employee-absence", metadata))
    end)
  end
end
```

After — a typed command plus a handler:

```elixir
defmodule Absence.Commands.AddEmployeeAbsence do
  use Absence.Command

  params do
    field :employee_id, :string
    field :absence_reason_id, :string
    field :start_date, :date
    field :end_date, :date
    field :comment, :string, optional: true
    # ...
  end

  handler Absence.AddEmployeeAbsence
end

defmodule Absence.AddEmployeeAbsence do
  use Absence, :application_service

  def execute(%Absence.Commands.AddEmployeeAbsence{} = command) do
    metadata = command.metadata

    # domain logic reads command.employee_id etc. ...

    start_transaction()
    |> persist_employee_absence(employee_absence)
    |> persist_event(event, metadata)
    |> finish_transaction()
    |> return_result()
  end

  defp persist_event(multi, event, metadata) do
    Multi.run(multi, :employee_absence_added_event, fn _, _ ->
      append_event(event, metadata)
    end)
  end
end
```

Helpers like `persist_event/3` take the metadata, not the whole command —
they need the append context, nothing else. Passing `%CommandKit.Metadata{}`
to `append_event` works because the struct enumerates as its flat
persistence map (our event stores call `Enum.into(metadata, %{})`).

And the call site (controller, LiveView, job):

```elixir
# before
Absence.AddEmployeeAbsence.execute(
  employee_id: employee_id,
  # ...
  metadata: event_metadata("add-employee-absence", enacted_by: current_user_urn)
)

# after
with {:ok, command} <- Absence.Commands.AddEmployeeAbsence.new(params) do
  command
  |> CommandKit.Command.enacted_by(current_user_urn)
  |> Absence.CommandBus.dispatch()
end
```

What changes:

- The command name string (`"add-employee-absence"`) disappears — it is
  derived from the module name. `Absence.Commands.AddEmployeeAbsence` derives
  `"add-employee-absence"`, so URNs in the event store stay identical to
  today's. If your module name does not match the historical command name,
  override `command_name/0` in the command module.
- The `event_metadata/2` ritual disappears — events inherit the command's
  metadata verbatim; `command.metadata` goes to `append_event` as-is.
- Params are validated and typed at construction; the handler never sees
  unparsed adapter input.
- `new/1` returns `{:error, %CommandKit.CommandError{}}` for invalid input,
  which the adapter layer maps to its own error responses.

### Handlers that append several events

Passing `command.metadata` on is not a byte-for-byte translation of
`event_metadata/2` — it fixes a subtle flaw. Today `for_command/2` generates
a **fresh URN per call**, so a chain-start service appending two events with
`event_metadata("add-employee-absence", ...)` and
`event_metadata("approve-employee-absence", ...)` produces two events with
*different* causation **and** correlation ids — they don't even correlate
with each other, and the second URN names a command that was never
dispatched. With CommandKit, every event a handler appends inherits the same
command metadata: one causation, one correlation, one chain. (Mid-chain
behavior is unchanged — incoming event correlation overrode the fresh URNs
today already.)

When one event should be caused by another event from the same handler —
event 2 caused by event 1 instead of by the command's cause — derive its
metadata with `caused_by_event`, which works inside handlers just as well as
in listeners:

```elixir
alias CommandKit.Metadata

added = EmployeeAbsenceAddedEvent.for(absence)

multi
|> Multi.run(:added, fn _, _ ->
  append_event(added, command.metadata)
end)
|> Multi.run(:approved, fn _, _ ->
  metadata =
    Metadata.caused_by_event(
      command.metadata,
      "employee-absence-added",
      added.id,
      Absence.Command
    )

  append_event(EmployeeAbsenceApprovedEvent.for(absence), metadata)
end)
```

Event 2's `causation_id` is the URN of event 1; `correlation_id` and
`enacted_by` are inherited from the command's metadata, so both events stay
in the same chain.

Repeat this step service by service. Services still on keyword lists and
services on CommandKit write metadata maps with identical keys and shape.

## Step 3: Inbound RabbitMQ consumers

Before — the consumer extracts correlation data by hand and passes it down:

```elixir
def consume(event) do
  metadata = extract_event_metadata(event)
  # causation_id = "#{event["type"]}:#{event["id"]}", correlation, actor, times...

  Absence.AddEmployeeAbsence.execute(
    employee_id: event["data"]["employee_id"],
    # ...
    metadata: metadata
  )
end
```

After — `caused_by/2` absorbs `extract_event_metadata/1`. Pass the raw
decoded CloudEvents map:

```elixir
def consume(event) do
  Absence.Commands.AddEmployeeAbsence.new!(params_from(event["data"]))
  |> CommandKit.Command.caused_by(event)
  |> Absence.CommandBus.dispatch()
end
```

This sets `causation_id` to the event's `"type:id"`, inherits its
`correlation_id` and `actor`, takes `occurred_at` from the event's time, and
sets `received_at` to consumption time. The event's own `causation_id` is
preserved automatically as the additional key `:original_causation_id` —
exactly what `extract_event_metadata/1` did with `original_causation_id`.

## Step 4: Internal listeners (event → command → event)

Listeners that react to your own persisted domain events move from directly
assembling metadata to dispatching a command.

Before — the listener derives metadata and appends directly:

```elixir
def handle_event(event, metadata) do
  new_metadata = metadata_caused_by_event("employee-absence-added", metadata)
  append_event(VacationDeductedEvent.for(...), new_metadata)
end
```

After — derive the metadata with `CommandKit.Metadata.caused_by_event/4`,
attach it with `with_metadata/2`, dispatch. The last argument is the command
base module: it carries the `source:` configuration, so the URN prefix stays
defined in one place:

```elixir
alias CommandKit.Metadata

def handle_event(event, metadata) do
  Absence.Commands.DeductVacation.new!(params_from(event))
  |> CommandKit.Command.with_metadata(
    Metadata.caused_by_event(metadata, "employee-absence-added", event.id, Absence.Command)
  )
  |> Absence.CommandBus.dispatch()
end
```

The handler appends follow-up events with `command.metadata` as in step 2.
Chain semantics stay correct: the resulting events' `causation_id` is the
URN of the triggering event — the command never appears mid-chain, because
commands are not persisted and could not be looked up. `occurred_at` and
`received_at` are set to derivation time: the follow-up event is a new fact.

Listeners that only produce events and never need a command skip the command
layer entirely:

```elixir
def handle_event(event, metadata) do
  derived = Metadata.caused_by_event(metadata, "employee-absence-added", event.id, Absence.Command)
  append_event(VacationDeductedEvent.for(...), derived)
end
```

## Step 5: Cleanup

Once no caller uses the old helpers anymore:

- delete `Shared.EventStore.Metadata`,
- delete `extract_event_metadata/1` from the consumer includes,
- remove `Shared.URN` calls that only served command metadata (URN helpers
  used for entity ids stay),
- remove the `event_metadata/2` import from the application-service includes.

A quick sweep finds leftovers:

```sh
grep -rn "event_metadata\|for_command\|caused_by_event\|extract_event_metadata" lib \
  | grep -v CommandKit
```
